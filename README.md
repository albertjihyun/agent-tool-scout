# agent-tool-scout

매주 월요일 아침, GitHub에서 새로 주목받은 AI 에이전트 도구를 골라 내 작업에 맞춰 정리한 리포트를 보내 주는 파이프라인입니다.

현재 상태: 설계 단계. 상세 설계는 [docs/design.md](docs/design.md)에 있습니다.

## 문제

Claude Code를 쓰면서 스킬이나 플러그인 하나가 작업 방식을 크게 바꾸는 경험을 했습니다. 그런데 이런 도구를 알게 되는 과정에는 두 가지 걸림돌이 있었습니다.

**첫째, 찾는 데 손이 많이 갑니다.** 새 도구는 GitHub 곳곳에 흩어져 올라오고, 무엇이 주목받는지 알려면 직접 뒤져야 합니다. 매주 그렇게 하기는 번거롭고, 결국 선배 개발자의 추천 같은 우연에 기대게 됩니다.

**둘째, 알게 되는 곳과 써 보는 곳이 다릅니다.** SNS에서 "이 스킬 좋다"는 글을 보는 건 주로 휴대폰으로 피드를 넘길 때입니다. 정작 도구를 설치하고 써 볼 수 있는 곳은 컴퓨터 앞, 터미널과 에디터가 열린 작업 공간입니다. 이 둘 사이의 거리 때문에 "나중에 해 봐야지"로 끝나고, 실제 설치까지 이어지지 않았습니다.

## 목표

정보를 찾는 수고를 없애고, 정보를 실행할 수 있는 시간과 장소에 전달하는 것이 목표입니다.

> 흩어진 AI 에이전트 도구 소식을 매주 대신 찾아, 내가 실행할 수 있는 시간과 장소로 가져온다.

- **찾는 일은 파이프라인이 대신합니다.** 매주 GitHub에서 주목받은 도구를 모으고 내 작업에 맞춰 거릅니다.
- **정해진 시간에, 작업 공간에서 받습니다.** 리포트는 매주 월요일 아침, 한 주를 시작하며 컴퓨터를 켰을 때 GitHub 이슈와 메일로 도착합니다. 읽는 곳이 곧 작업하는 곳이라 관심이 생긴 도구는 그 자리에서 바로 써 볼 수 있습니다.
- **바로 따라 할 수 있게 씁니다.** 항목마다 설치 명령어와 내 작업에서의 활용 포인트를 담아서, 읽은 직후 써 보는 데 필요한 정보를 다 갖추게 합니다.

리포트는 결론이 아니라 판단의 재료입니다. 무엇인지, 어디에 쓸 수 있는지를 짧게 전하고, 더 깊이 공부할지는 읽는 사람이 정합니다.

매주 같은 시간에 리포트가 온다는 것 자체가 새 도구를 살펴보는 습관을 만드는 장치가 됩니다. 그래서 이 프로젝트의 성공 기준은 "몇 개를 설치했는가"가 아니라 "리포트가 매주 빠짐없이 정확하게 도착하는가"입니다. 실패했을 때 조용히 넘어가지 않고 반드시 알림이 오는 것까지 포함합니다.

## 설계 원칙

**정해진 경로로 처리할 수 있는 일은 코드가, 미리 정할 수 없는 판단은 에이전트가 맡습니다.**

GitHub에서 후보를 모으고, 스타 증가량을 계산하고, 이미 소개한 레포를 거르는 일은 같은 입력에 항상 같은 결과가 나와야 합니다. 이런 일을 LLM에 맡기면 비용만 들고 결과는 불안정해집니다. 반면 "이 레포가 내 작업과 관련이 있는가", "더 조사할 가치가 있는가", "내 환경에서 어떻게 쓸 수 있는가"는 레포마다 확인할 경로가 달라서 코드로 분기를 다 짤 수 없습니다. 이 부분만 에이전트에게 맡깁니다.

에이전트에게 넘기는 후보는 코드가 미리 30개 안팎으로 줄여 둡니다. 에이전트가 GitHub 전체를 헤매지 않으니 사용량을 예측할 수 있습니다.

**비용은 Claude 구독 하나로 통일합니다.** API 키를 쓰지 않고, Claude Code를 구독 토큰으로 실행합니다. 매주 계속 돌아가야 하는 도구라서 사용할수록 과금이 늘어나는 구조를 피했습니다.

**멀티 에이전트는 필요가 확인될 때만 도입합니다.** 처음에는 에이전트 하나로 시작하고, 실제 실행에서 맥락이 넘치거나 품질이 떨어지는 것이 확인되면 조사 전담 하위 에이전트를 추가합니다.

## 리포트 구성

리포트는 두 섹션과 별첨으로 나뉩니다.

1. **이번 주 뜬 AI 에이전트 도구 (최대 5개)**. 내 Claude Code 작업에 바로 가져다 쓸 수 있는 스킬, 플러그인, MCP 서버, 개발 도구를 다룹니다. 항목마다 무엇인지, 왜 이번 주에 떴는지, 내 활용 포인트, 설치 방법, 더 볼 곳을 3분 안에 읽을 분량으로 씁니다. 활용 포인트는 레포의 `profile.md`에 적힌 내 관심사를 기준으로 작성됩니다.
2. **Claude Code 공식 업데이트**. 지난 한 주의 릴리스에서 새 기능과 사용 방식이 바뀐 부분만 고릅니다. 변경이 없는 주에도 섹션을 빼지 않고 "주요 변경 없음"이라고 적습니다. 그래야 수집 실패와 구분할 수 있습니다.
3. **별첨: 범위 밖이지만 주목할 것 (0~3개)**. 에이전트 프레임워크나 새 AI 모델처럼 내 작업에 바로 쓰긴 어렵지만 흐름으로 알아 둘 만한 것을 한두 줄씩 남깁니다. 섹션 1의 후보를 검토하는 과정에서 나오므로 따로 수집하지 않습니다.

처음에는 GitHub 전체의 스타 증가 순위를 별도 섹션으로 두려 했습니다. 그런데 실제 상위권을 확인해 보니 의미 있는 항목은 대부분 AI와 에이전트 분야라서 섹션 1의 후보에 이미 들어 있었고, 나머지는 기술과 무관하거나 스타가 부풀려진 것으로 보이는 레포였습니다. 그래서 별도 섹션 대신 별첨으로 흡수했습니다.

이미 소개한 레포는 다시 소개하지 않습니다. 일반 앱, awesome 목록의 신규 항목, 커뮤니티 이슈는 목적과 거리가 멀어 다루지 않습니다.

## 동작 방식

GitHub Actions에서 매주 한 번 세 단계로 실행됩니다. 별도 서버는 없습니다.

```
1. 수집 (Python)      후보 수집, 7일 스타 증가량 계산, 필터링
2. 분석 (Claude Code)  후보 선별, 추가 조사, 리포트 작성
3. 발행 (Python)      리포트 검증, 레포에 저장, 이슈 생성 → 메일 알림
```

분석 단계가 실패하거나 사용 한도에 걸려도 수집한 데이터는 저장하고, 분석 없이 후보 목록만 담은 리포트를 보냅니다. 다음 주 증가량 계산이 끊기지 않게 하기 위해서입니다.

## 데이터 출처를 고른 이유

GitHub API는 "이번 주에 스타가 몇 개 늘었는가"를 레포 단위로만 알려 주고, 순위는 주지 않습니다. 그래서 후보를 먼저 모은 뒤 증가량을 직접 계산합니다.

- 후보 수집에는 GitHub 검색 API와 Trendshift를 함께 씁니다. 실제로 비교해 보니 검색만으로는 주목받은 레포 일부를 놓쳤고, 그 레포들은 Trendshift에 잡혀 있었습니다.
- 증가량은 매주 저장한 스타 수를 비교해서 구하고, 새로 후보에 들어온 레포만 GitHub의 스타 히스토리 API로 조회합니다. 후보가 수천 개라서 전부 히스토리로 조회하면 API 한도를 넘기 때문입니다.
- GitHub Trending 주간 페이지는 robots.txt가 수집을 막고 있어 쓰지 않습니다. OSS Insight와 GH Archive는 2026년 3월 이후 GitHub 이벤트 데이터 수집이 사실상 끊겨 쓰지 않습니다.

조사 과정과 수치는 [docs/research](docs/research/)에 남겨 두었습니다.

## 한계

- 스타는 관심도이지 실사용이 아닙니다. 포크, 이슈, 커밋 같은 보조 신호로 보완하지만 완전하지 않습니다.
- 후보 풀 밖에서 급상승한 레포는 놓칠 수 있습니다. GitHub 전체를 전수 조사할 공개 데이터가 현재는 없습니다.
- Trendshift는 개인이 운영하는 사이트라 언제든 바뀔 수 있습니다. 그래서 GitHub 검색만으로도 동작하도록 설계했습니다.
- AI와 에이전트 분야 밖의 기술 흐름은 다루지 않습니다.

P.S. 제가 쓰려고 만든 도구지만, 관심사, 검색 키워드, 리포트 언어, 실행 일정 같은 개인 값은 `profile.md`와 설정 파일 하나에 모아 두었습니다. 같은 리포트를 받아 보고 싶다면 레포를 포크해서 이 파일들을 고치고 자신의 구독 토큰을 넣으면 됩니다.
