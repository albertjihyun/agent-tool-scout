# agent-tool-scout 설계

작성일: 2026-10-25
상태: 승인됨

이 문서는 구현자를 위한 상세 설계다. 공개용 기획 설명은 README에 있다. "소유자 결정"은 레포 소유자가 직접 정한 것이고, "구현자 판단"은 설계 논의 중 기본값으로 정한 것이라 근거가 있으면 바꿀 수 있다.

## 1. 의도

소유자는 백엔드 개발자이고 AI와 업무 자동화에 관심이 많다. 유용한 도구를 알게 되는 과정에 두 가지 걸림돌이 있었다.

1. **찾는 데 손이 많이 간다.** 새 도구는 GitHub 곳곳에 흩어져 있고 매주 직접 뒤지기 번거로워서, 선배 개발자의 추천 같은 우연에 기대게 된다.
2. **알게 되는 곳과 써 보는 곳이 다르다.** SNS에서 도구 소식을 보는 건 주로 휴대폰이고, 설치하고 써 볼 수 있는 곳은 컴퓨터의 작업 공간이다. 이 거리 때문에 정보가 행동으로 이어지지 않았다.

그래서 이 프로젝트는 찾는 일을 파이프라인이 대신하고, 결과를 실행할 수 있는 시간과 장소로 가져온다. 매주 월요일 아침, 한 주를 시작하며 컴퓨터를 켰을 때 GitHub 이슈와 메일로 리포트가 도착한다. 읽는 곳이 곧 작업하는 곳이므로 각 항목에는 바로 따라 할 수 있는 설치 명령어와 활용 포인트를 담는다.

리포트는 판단을 끝내는 곳이 아니라 입구다. 더 깊이 공부할지는 소유자가 정한다. 매주 같은 시간에 도착하는 리포트가 새 도구를 살펴보는 습관을 만드는 장치이므로, 제때 빠짐없이 도착하는 것이 무엇보다 중요하다. 성공 기준(3장)과 실패 처리(9장)는 여기서 나온다.

목적 문장:
> 흩어진 AI 에이전트 도구 소식을 매주 대신 찾아, 내가 실행할 수 있는 시간과 장소로 가져온다.

## 2. 설계 원칙 (소유자 결정)

1. **로직과 에이전트의 경계.** 같은 입력에 같은 결과가 나와야 하는 일(수집, 계산, 필터, 발행)은 코드가 한다. 경로를 미리 정할 수 없는 판단(무엇이 관련 있는지, 무엇을 더 조사할지, 소유자의 작업에 어떻게 쓸지)만 에이전트가 한다. 이 경계와 그 이유가 이 프로젝트의 핵심 결과물이다. 단순 자동화를 에이전트라고 부르지 않는다.
2. **비용은 Claude 구독 하나로.** API 키를 만들지 않는다. 추가 과금이 생기는 경로를 두지 않는다. Claude 호출은 Claude Code + `CLAUDE_CODE_OAUTH_TOKEN`(`claude setup-token`으로 생성, 유효기간 1년)으로만 한다. LangGraph 등 API 키가 필요한 방식은 쓰지 않는다.
3. **멀티 에이전트는 필요가 확인될 때만.** 처음에는 에이전트 하나로 시작한다. 실제로 돌려 보고 맥락이 넘치거나 품질이 떨어질 때 하위 에이전트(`.claude/agents/researcher.md`)를 추가한다.

## 3. 목표, 하지 않는 것, 실패로 보는 것

**목표**
- 매주 월요일 아침에 리포트가 빠짐없이 도착한다.
- 리포트의 데이터(스타 증가량 등)가 정확하다.

**성공 기준 (소유자 결정)**: 몇 개를 설치했는지로 성공을 재지 않는다. 리포트가 매주 제대로 오는 것이 기준이다.

**하지 않는 것 (소유자 결정)**
- 일반 앱(셀프호스팅 앱 등)을 섹션 1에서 다루지 않는다.
- awesome 목록 등 큐레이션 목록의 신규 항목 추적은 하지 않는다.
- Hacker News, Reddit 등 커뮤니티 이슈 수집은 하지 않는다.
- GitHub 전체 스타 증가 순위를 별도 섹션으로 다루지 않는다(4장 끝 참고).
- 이전 리포트에 소개한 레포를 다시 소개하지 않는다.

**실패로 보는 것**
- 리포트가 조용히 오지 않는 것. 실패하면 반드시 메일로 알 수 있어야 한다.
- 스타 수 부풀리기 레포를 아무 표시 없이 추천하는 것.
- 사용량 폭주로 소유자의 주간 Claude 사용 한도를 크게 잠식하는 것.

## 4. 리포트 구성 (소유자 결정)

리포트 언어는 설정 파일의 `report_language`로 정한다(소유자는 `ko`). 전체를 약 20분 안에 읽을 수 있는 분량.

### 섹션 1. 이번 주 뜬 AI 에이전트 도구

- 범위: 소유자가 Claude Code 작업에 가져다 쓸 수 있는 것. 스킬, 플러그인, MCP 서버, 개발 도구(CLI, 에이전트 프레임워크, 라이브러리), 기타로 분류한다. 일반 앱은 제외한다.
- 개수: 최대 5개. 해당이 적은 주에는 5개보다 적어도 된다.
- 항목당 3분 안에 이해되는 분량. 기술 세부사항보다 개념과 활용 위주.
- 항목 형식:
  1. 무엇인지 (두세 줄)
  2. 왜 이번 주에 떴는지 (7일 스타 증가량, 스타 외 신호로 본 실사용 여부)
  3. 활용 포인트 (`profile.md` 기준 개인화)
  4. 설치 및 연결 방법 (명령어 그대로)
  5. 더 볼 곳 (공식 문서, 레포 링크)

### 섹션 2. Claude Code 공식 업데이트

- 출처: `anthropics/claude-code`의 지난 7일 릴리스.
- 버그 수정과 내부 변경은 빼고 새 기능과 사용 방식 변화만 남긴다(이 거르기는 에이전트가 한다).
- 기능마다 한두 줄 설명과 "써 보려면" 명령어 한 줄.
- 해당 릴리스가 없으면 "이번 주 주요 변경 없음" 한 줄. 섹션을 빼지 않는다. 수집 실패와 구분하기 위해서다.

### 별첨. 범위 밖이지만 주목할 것

- 목적: Claude Code 작업에 바로 쓰긴 어렵지만 AI·에이전트 분야의 흐름으로 알아 둘 만한 것을 짧게 남긴다. 예: 에이전트 프레임워크(LangGraph류), 새 AI 모델·추론 엔진.
- 0~3개, 항목당 한두 줄로 "무엇이고 어떤 흐름의 일부인지". 해당이 없는 주에는 "이번 주 해당 없음" 한 줄.
- 재료는 섹션 1과 같은 후보 풀이다. 별도 수집을 하지 않는다. 에이전트가 섹션 1 후보를 검토하다가 범위 밖이지만 의미 있는 것을 여기에 둔다.
- 섹션 1에 실은 레포는 별첨에 싣지 않는다. 3단계 검증에서 중복이 있으면 별첨 쪽을 제거한다.

### 섹션 3(GitHub 전체 최상위)을 두지 않는 이유 (소유자 결정)

처음에는 GitHub 전체 스타 증가 상위를 별도 섹션으로 두려 했다. 2026-10-24 조사에서 전체 상위권 중 의미 있는 항목은 대부분 AI·에이전트 분야여서 섹션 1 후보 풀에 이미 잡히고, 나머지는 기술과 무관한 레포나 스타 부풀리기 의심 레포였다. 프로젝트 이름과 목적(에이전트 도구)에도 맞지 않아 별도 섹션 대신 별첨으로 흡수했다. 대가로 AI와 무관한 기술 흐름은 리포트에서 보이지 않는다.

## 5. 전체 흐름

```
GitHub Actions (매주 cron + 수동 실행)
 ├─ 1단계 collect (Python, Claude 사용 없음)
 │    후보 수집 → 7일 증가량 계산 → 필터 → data/candidates.json
 ├─ 2단계 analyze (Claude Code, 구독 사용량)
 │    candidates.json + profile.md + 프롬프트 → reports/draft.md
 └─ 3단계 publish (Python)
      리포트 검증 → 이슈 생성(메일 알림)
      data 브랜치에 리포트 사본·스냅샷·소개 이력 커밋
```

실행 환경은 GitHub Actions 러너다. 별도 서버를 두지 않는다. 공개 레포라 Actions 실행 시간은 무료다.

### 브랜치 역할 (소유자 결정)

| 브랜치 | 내용 | 누가 바꾸나 |
|---|---|---|
| `main` | 코드, 문서, 프롬프트, 설정 | 소유자만, PR로만 |
| `data` | `data/`(스냅샷, 소개 이력, 후보), `reports/`(리포트 사본) | 봇만, 직접 커밋 |

- 이유: 봇이 main에 매주 커밋하면 소유자의 변경 기록 사이에 봇 커밋이 1년에 52개씩 끼고, main에 "PR 필수" 규칙을 걸 수 없다. 봇 데이터를 별도 브랜치로 분리하면 main은 PR로만 바뀌고 기록도 깔끔하다.
- `data` 브랜치는 main과 히스토리를 공유하지 않는 고아(orphan) 브랜치로 만든다. 코드는 들어 있지 않다.
- 워크플로우는 main을 체크아웃해 코드를 실행하고, `data` 브랜치를 별도 경로(예: `./_data`)에 체크아웃해 읽고 쓴다.
- 리포트는 이슈로 읽는다. `data` 브랜치의 `reports/`는 보관용 사본이다.
- 보호 규칙: main은 PR 필수 + 강제 push·삭제 금지. `data`는 강제 push·삭제 금지만(봇의 일반 커밋은 허용).

## 6. 1단계: 수집 (로직)

### 6.1 7일 스타 증가량 계산

- 기간: 실행 시점 기준 완료된 최근 7일(UTC). 모든 출처의 주 경계를 이 정의 하나로 맞춘다.
- **스냅샷 비교가 기본**: 검색 API 결과에 각 레포의 현재 스타 수(`stargazers_count`)가 들어 있다. 매주 후보 전체의 스타 수를 `data/snapshots/YYYY-MM-DD.json`에 저장하고, 지난주 스냅샷과 빼서 증가량을 구한다.
- **스타 히스토리 API는 보조**: `GET /repos/{owner}/{repo}/stargazers/history`(헤더 `X-GitHub-Api-Version: 2026-03-10`). 지난주 스냅샷에 없는 레포(새로 생겼거나 하한을 막 넘은 레포)와 첫 실행에서만 쓴다. 응답 형식과 계산법은 `docs/research/global-top-sources.md` 참고.
- 이유: 후보가 수천 개라 전부 스타 히스토리로 조회하면 `GITHUB_TOKEN` 한도(시간당 1,000회)를 넘는다. 검색은 한 번에 100개씩 스타 수를 주므로 수천 개도 수십 번 호출로 끝난다.
- 스냅샷 간격이 정확히 7일이 아닐 수 있다(cron 지연, 수동 실행). 구현자가 보정 방식을 정한다(일 단위 환산, 또는 간격이 크게 어긋나면 스타 히스토리로 대체 등). 비교 기준은 "7일 전에 가장 가까운 정식 실행 스냅샷"으로 한다.
- **API 한도 처리 (구현자 판단)**: 개인 토큰 없이 `GITHUB_TOKEN`만 쓴다. 관리할 secret과 만료일을 늘리지 않기 위해서다.
  - 첫 실행 문제: 첫 실행에는 모든 후보가 지난주 스냅샷에 없어서 수천 건 조회가 필요하다. 그래서 첫 정식 리포트 전에 스냅샷만 저장하는 실행(부트스트랩)을 한 번 한다. 개발 중에 수동으로 실행해 두면 첫 월요일에는 스냅샷 비교로 증가량을 낼 수 있다.
  - 매주 새로 후보에 들어온 레포의 스타 히스토리 조회는 상한(예: 600회)을 둔다. 상한을 넘으면 현재 스타가 많은 순으로 조회하고, 생성된 지 7일 이내인 레포는 조회 없이 현재 스타 수를 증가량으로 본다. 상한에 걸린 사실은 수집 메타데이터에 남긴다.

### 6.2 섹션 1 후보 풀

- GitHub 검색, 이름·설명 키워드 두 묶음:
  - `claude OR skill OR skills OR mcp OR codex OR agentic in:name,description`
  - `agent OR agents OR cursor OR copilot OR opencode OR harness in:name,description`
- 보조: 토픽 검색(`claude-code`, `agent-skills`, `mcp`, `mcp-server`, `ai-agents`, `codex`, `claude-skills`), README 키워드 검색.
- 검색 결과가 1,000개 제한에 걸리면 스타 구간을 나눠 전부 열거한다.
- 검색으로 못 잡는 레포 보완: Trendshift 주간·일간 목록(`https://trendshift.io/weekly`, `https://trendshift.io/`)을 키워드로 걸러 합친다. Trendshift는 7일 증가량(`repository_stars_gained`)을 함께 주므로 스타 히스토리 조회 없이 참고값으로 쓸 수 있다. 파싱 방법은 `docs/research/global-top-sources.md` 참고. Trendshift가 실패하거나 파싱 결과가 15개 미만이면 기록만 남기고 검색만으로 계속한다.
- 쓰지 않는 출처: GitHub Trending의 `?since=weekly`(robots.txt 금지), OSS Insight와 GH Archive(2026-03 이후 데이터 수집 붕괴).
- 스타 하한, 생성일·push 조건 같은 숫자는 구현자가 실제 실행으로 조정한다. 참고 수치(2026-10-25 측정, 최근 1년 생성 + 최근 7일 push): 키워드 묶음 1 기준 스타 200+ 2,623개, 500+ 1,499개, 1,000+ 938개.
- 조사 근거: `docs/research/candidate-discovery.md`. 키워드 검색 단독으로 핵심 레포 39개 중 33~35개를 잡았고, 놓친 것은 트렌딩 출처에 있었다.

### 6.3 필터와 보강

- 이전에 소개한 레포 제외: `data/reported.json`(레포 이름, 소개한 주, 섹션 1 또는 별첨)에 있는 레포는 제외.
- 증가량 상위 약 25~30개를 에이전트에게 넘긴다. 섹션 1의 5개와 별첨 0~3개를 고를 재료가 되도록 섹션 1만 있을 때보다 조금 넉넉하게 잡는다.
- 넘기는 후보마다 보강할 정보(레포 API로 수집): 설명, 토픽, 총 스타, 7일 증가량, 포크 수, 열린 이슈 수, 마지막 push, 생성일, 라이선스, 홈페이지.
- 로직으로 가능한 분류 힌트: 루트 또는 하위에 `SKILL.md`가 있으면 스킬, `.claude-plugin/`이 있으면 플러그인, 토픽에 `mcp-server`가 있으면 MCP 서버. 힌트로 확정된 분류는 에이전트가 바꾸지 않는다. 나머지 분류는 에이전트가 한다.
- 부풀리기 의심 표시: 7일 증가량에 비해 포크, 이슈, 커밋 활동이 현저히 적은 경우. 기준값은 구현자가 정한다.
- 섹션 2: `anthropics/claude-code` 릴리스 중 기간 내 것을 본문 그대로 수집.

출력: `data/candidates.json` (섹션별 후보와 보강 정보, 수집 메타데이터: 출처별 성공 여부, 호출 수).

## 7. 2단계: 분석 (에이전트)

- 실행: `anthropics/claude-code-action`, 인증은 `claude_code_oauth_token: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}`.
- 입력: `data/candidates.json`, `profile.md`, `prompts/weekly-report.md`, 설정 파일의 리포트 언어.
- 에이전트가 판단하는 것:
  - 섹션 1: 후보 중 범위에 맞는 최대 5개 선택, 분류, 필요한 만큼 README·문서·관련 글을 더 조사, 항목 작성.
  - 섹션 2: 릴리스 노트에서 소유자에게 의미 있는 변경 고르기.
  - 별첨: 섹션 1 범위 밖이지만 흐름으로 알아 둘 만한 것 0~3개 고르고 한두 줄 해설. 깊이 조사하지 않는다.
- 사용량 예산 (소유자 결정, 잠정): 한 번 실행에 Pro 주간 한도의 약 5% 이내를 출발점으로 한다. 첫 테스트 실행에서 실제 사용량을 재고 소유자와 다시 정한다. Actions 실행은 claude.ai 클라우드 크레딧이 아니라 구독 주간 한도에서 차감된다.
- 허용 도구: 파일 읽기, `reports/draft.md` 쓰기, 웹 검색, 웹 페이지 읽기. 레포 파일 수정, git 명령, 임의 셸 실행은 허용하지 않는다.
- 사용량 상한: 최대 턴 수를 둔다. 값은 구현자가 실제 실행으로 정한다. 실행마다 사용량(턴 수, 소요 시간)을 Actions 요약에 남겨 추이를 본다.
- 출력 형식: 템플릿(`prompts/report-template.md`)을 따르는 마크다운. 3단계가 검증할 수 있도록 섹션 구분을 고정한다. 제목 문구는 리포트 언어에 따라 달라질 수 있으므로, 검증은 번역된 제목이 아니라 고정된 표시(예: HTML 주석 마커)로 섹션을 알아본다.

### profile.md (소유자 결정: 개인화 포함)

에이전트가 "활용 포인트"를 쓰는 근거. 초기 내용:
- 백엔드 개발자, AI와 업무 자동화에 관심, 전 세계 최신 기술 흐름을 따라가고 싶음
- 사용 중인 도구: Claude Code, superpowers 플러그인

소유자가 직접 고쳐 쓰는 파일이다.

## 8. 3단계: 발행 (로직)

- `reports/draft.md`가 있고 필수 섹션이 모두 있으면 `data` 브랜치의 `reports/YYYY-Www.md`로 저장.
- 이슈 생성: 제목은 설정 파일의 형식을 따른다(소유자는 `[주간 리포트] 2026년 10월 4주차` 형식). 본문은 리포트 전문, 라벨 `weekly-report`. 작성자가 `github-actions[bot]`이어야 레포 소유자에게 메일 알림이 간다(소유자 본인 토큰으로 올리면 본인에게는 알림이 가지 않는다).
- `data/reported.json` 갱신(섹션 1과 별첨에 실제로 실린 레포). 분석 실패 리포트의 후보 목록은 기록하지 않는다. 분석된 적 없는 레포가 영원히 제외되면 안 되기 때문이다.
- 스냅샷과 이력은 2단계 성공 여부와 관계없이 커밋한다. 다음 주 증가량 계산이 끊기지 않게 하기 위해서다.
- 커밋은 봇이 `data` 브랜치에만 한다. main에는 커밋하지 않는다(5장 브랜치 역할 참고).

## 9. 실패 처리

| 상황 | 동작 |
|---|---|
| 1단계 실패 (GitHub API 오류 등) | 워크플로우 실패 → GitHub의 "Run failed" 메일로 알림 |
| Trendshift만 실패 | 기록만 남기고 GitHub 검색으로 계속. 리포트 하단에 "일부 출처 실패" 표시 |
| 2단계 실패 또는 사용량 한도 초과 | 분석 없이 후보 목록만 담은 리포트로 이슈 생성, 제목에 분석 실패 표시. 스냅샷은 저장 |
| 리포트 형식 검증 실패 | 위와 동일하게 처리하고 원본 draft는 남긴다 |

## 10. 실행 설정 (구현자 판단)

- 일정: 매주 월요일 오전(한국 시간). GitHub의 정시 cron은 지연이 잦으니 정시를 피한 시각으로 둔다. 예: `17 23 * * 0`(UTC 일요일 23:17 = 한국 월요일 08:17).
- `workflow_dispatch`로 수동 실행 가능. 실행 모드를 입력으로 받는다:
  - `dry-run` (수동 실행 기본값): 리포트를 Actions 아티팩트로만 남긴다. 스냅샷, 소개 이력 커밋과 이슈 생성을 하지 않는다. 개발 중 테스트가 다음 주 증가량과 소개 이력을 오염시키지 않게 하기 위해서다.
  - `bootstrap`: 스냅샷만 저장하고 분석과 발행은 하지 않는다.
  - `full`: 정식 실행과 같다. cron 실행은 항상 `full`.
  - `skip-analysis` 옵션: 수집과 발행 로직만 시험할 때 2단계를 건너뛰어 구독 사용량을 아낀다.
- 권한: `contents: write`, `issues: write`.
- 보안: `pull_request_target`을 쓰지 않는다. 외부 포크 PR에 secret이 전달되지 않는 기본값을 유지한다.
- OAuth 토큰은 1년 후 만료된다. 만료 시 2단계가 실패하고 분석 실패 리포트가 온다. README에 갱신 방법을 적는다.
- 언어: Python. 테스트는 수집 로직(증가량 계산, 필터, 파싱)과 발행 로직(검증, 이력 갱신) 위주로 작성한다.

## 12. 첫 작업으로 확인할 것

1. 이슈 메일 알림: 봇이 이슈를 올리는 테스트 워크플로우를 수동 실행해서 소유자 메일로 오는지 확인.
2. Actions(Azure IP)에서 Trendshift 접속이 막히지 않는지.
3. 구독 토큰으로 claude-code-action이 도는지, 한 번 실행에 사용량이 얼마나 드는지.

확인이 실패할 때의 대안 (구현자 판단):
- 봇 이슈 메일이 오지 않으면: 이슈 본문에 봇이 소유자(`config.yml`의 값)를 멘션한다. 멘션은 "Participating, @mentions" 알림 경로로 메일이 가며, 소유자 설정에서 이 경로의 메일은 켜져 있다. secret이 늘지 않는다.
- 구독 토큰으로 2단계가 돌지 않으면: API 키로 바꾸지 않는다(원칙 2). 분석 없는 후보 리포트로 운영하면서 원인을 찾고, 방향은 소유자와 다시 정한다.

## 13. 알려진 한계

- 스타는 관심도이지 실사용이 아니다. 보조 신호(포크, 이슈, 커밋)로 보완하지만 완벽하지 않다.
- Trendshift는 1인 운영 사이트라 언제든 바뀌거나 멈출 수 있다. GitHub 검색만으로도 돌아가게 설계했다.
- 후보 풀 밖에서 급상승한 레포는 놓칠 수 있다. 공개 이벤트 스트림이 사라져서 GitHub 전체를 전수 조사할 방법이 없다.
- AI·에이전트와 무관한 기술 흐름은 다루지 않는다.
- 스타 히스토리 API는 2026-09 신규라 버전이 바뀔 수 있다.

## 14. 포크해서 쓸 수 있게 (소유자 결정, 가벼운 목표)

주목표는 아니지만, 다른 사람이 포크해서 쓸 수 있게 개인 값을 코드에 박지 않는다. 멘션할 사용자 이름, 검색 키워드와 토픽, 스타 하한, 후보 개수, 리포트 언어, 이슈 제목 형식 등은 설정 파일 하나(`config.yml`)와 `profile.md`로 모은다. cron 시각은 워크플로우 파일에 있어야 하므로 예외로 하고 README에 고치는 위치를 적는다. README에는 P.S. 정도로만 언급한다. 스킬로 포장(`/scout` 등)하는 것은 범위 밖이며 파이프라인 안정화 후 별도로 검토한다.

- 스냅샷 간격 보정 방식
- 프롬프트와 템플릿의 세부 문구

- 파이썬 패키지 구조와 라이브러리 선택
